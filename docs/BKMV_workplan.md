# תוכנית עבודה — מבנה אחיד (BKMV) ב-app.ux

נכתב 29/07/2026 · מקור: "הוראות להפקת קבצים במבנה אחיד", רשות המסים, **גרסה 1.31** (10.05.2009), בצירוף קטעי סעיפים 2.6 ו-5.4 ודוגמת פלט הסימולטור.

**המשימה הזו נפרדת ולא חוסמת את שע"ם.** הקצאת מספרי חשבוניות עובדת בלי קשר לייצוא. אין להתחיל אותה לפני שההקצאה עובדת בפרודקשן.

---

## מצב קיים — סיכום כן

המודול `lib/regulatory/bkmv/` הוא **שלד מוצהר**, 408 שורות סה"כ. מה שקיים:

| רכיב | מצב |
|---|---|
| `spec.ts` | מצהיר על עצמו כלא שלם. כל רשומה מכילה שדה אחד בלבד (`record_code`). |
| `assertBkmvSpecComplete()` | **מסרב להריץ ייצוא כל עוד ה-spec חסר.** זו החלטה נכונה — נכשל בקול ולא מייצר קובץ שגוי. |
| `build.ts` | בונה A100 → B100/B110 ריקות → C100/D110/D120 לכל מסמך → Z900 עם `total_docs` בלבד. |
| `zip.ts` | אורז **רק `BKMVDATA.TXT`**. אין `INI.TXT`. |
| `encoding.ts` | Windows-1255 + CRLF — קיים. |
| נתיב API | `app/api/regulatory/bkmv/export` + `download`, עם rate limit ואחסון פר-חברה. |

התשתית נכונה. מה שחסר הוא התוכן הרגולטורי.

**באג בשם הגרסה:** `BKMV_SPEC_VERSION = "5.4-TBD"`. "5.4" הוא **מספר סעיף** במסמך ההוראות, לא מספר גרסה. הגרסה במסמך שהתקבל היא **1.31**. לתקן, ולוודא מול gov.il שזו הגרסה העדכנית לפני שמשקיעים בקידוד הטבלאות.

**מוכן כאשר:** מספר הגרסה מאושר ורשום ב-`BKMV_SPEC_VERSION`.

## שלב 1 — קידוד טבלאות השדות (עיקר העבודה)

זהו הלב. לכל סוג רשומה יש טבלה במסמך ההוראות עם: מספר שדה, שם, סוג (נומרי/אלפאנומרי), אורך, ומיקום התחלה. אורכי הרשומות לפי המסמך:

| קובץ | רשומה | תיאור | אורך |
|---|---|---|---|
| `INI.TXT` | `A000` | רשומה מרכזת | 466 |
| `INI.TXT` | `B100`/`B110`/`C100`/`D110`/`D120`/`M100` | רשומות סיכום, אחת לכל סוג | 19 כל אחת |
| `BKMVDATA.TXT` | `A100` | רשומת פתיחה | 95 |
| `BKMVDATA.TXT` | `B100` | תנועות בהנהלת חשבונות | 317 |
| `BKMVDATA.TXT` | `B110` | חשבון בהנהלת חשבונות | 376 |
| `BKMVDATA.TXT` | `C100` | כותרת מסמך | 444 |
| `BKMVDATA.TXT` | `D110` | פרטי מסמך | 339 |
| `BKMVDATA.TXT` | `D120` | פרטי קבלה/הפקדה | 222 |
| `BKMVDATA.TXT` | `M100` | פריט במלאי | 298 |
| `BKMVDATA.TXT` | `Z900` | רשומת סגירה | — |

כללי מילוי מהמסמך שחייבים להיות מקודדים ב-`format.ts`:

- שדות נומריים — יישור לימין, ריפוד באפסים.
- שדות אלפאנומריים — יישור לשמאל, ריפוד ברווחים.
- אורך שורה קבוע, סיום `CRLF`, קידוד Windows-1255 (קיים).
- לכל רשומה שדה "מספר רשומה בקובץ" — מספר רץ.
- סכומים ב-`B100` (שדות 1368, 1369) ו-`B110` (שדה 1414) — כללי סימן מיוחדים, ראה סעיף י"א.
- ב-`C100`/`D110` ערכים שליליים — ראה סעיף י"ב.

**מוכן כאשר:** `assertBkmvSpecComplete()` עוברת, ולכל רשומה יש טבלת שדות מלאה עם בדיקת אורך אוטומטית שמוודאת שהשורה שנוצרה שווה בדיוק לאורך שבטבלה.

**המלצה:** לכתוב בדיקת יחידה אחת לכל סוג רשומה שבונה שורה מדוגמה ומאמתת אורך ומיקומים. בלי זה, שגיאת ריפוד אחת מרעילה את כל הקובץ בשקט.

## שלב 2 — `INI.TXT` והמזהה הראשי

`INI.TXT` לא קיים כלל היום. הוא מכיל רשומה מובילה אחת (`A000`) ורשומת סיכום לכל סוג רשומה שקיים ב-`BKMVDATA.TXT`.

**המזהה הראשי:** מספר רנדומלי בן 15 ספרות, שחייב להיות **זהה** בשלושה מקומות — שדה `1004` ב-`INI.TXT`, שדה `1103` ברשומת הפתיחה `A100`, ושדה `1153` ב-`Z900`. זה הדבר הראשון שבודקים בביקורת. לייצר פעם אחת פר-ייצוא ולהעביר אותו לשלושת המקומות ממקור אחד.

**מוכן כאשר:** נוצרים שני קבצים, המזהה זהה בשלושתם, וספירות הסיכום ב-`INI.TXT` תואמות בדיוק לספירות בפועל ב-`BKMVDATA.TXT`.

## שלב 3 — החלטה: `B100`, `B110`, `M100`

כרגע `B100` ו-`B110` נכתבות כרשומות **ריקות**. זו סתירה: אין במערכת מודול הנהלת חשבונות ואין מלאי, ולכן אין תנועות יומן, אין כרטסת ואין פריטים.

הכיוון הנכון: **לא לכתוב את הרשומות האלה בכלל**, ולרשום ב-`INI.TXT` סיכום 0 לכל אחת מהן. רשומה ריקה באורך 317 תווים היא הצהרה שקיימת תנועת יומן ריקה — וזה גרוע מהיעדרה.

**לאימות מול המסמך לפני היישום.** זו החלטה רגולטורית, לא העדפה.

**מוכן כאשר:** קובץ שנוצר לעסק ללא הנהלת חשבונות מכיל `A100`, `C100`, `D110`, `D120`, `Z900` בלבד, ו-`INI.TXT` מצהיר 0 ל-`B100`/`B110`/`M100`.

## שלב 4 — שמות קבצים ומבנה תיקיות

המסמך מגדיר מבנה מדויק שלא ניתן לאלתר:

```
<כונן>\OPENFRMT\<מספר עוסק>.<שנה>\<תאריך ושעה>\
   ├── INI.TXT
   └── BKMVDATA.zip   (ה-BKMVDATA.TXT מכווץ)
```

לדוגמה מהמסמך: `F:\OPENFRMT\00223344.08\09111025`. שני ייצואים באותו יום יוצרים שתי תיקיות נפרדות לפי השעה.

במערכת ענן אין "כונן", ולכן המבנה הזה חייב להשתקף **בתוך ה-ZIP שהמשתמש מוריד**, כך שכשהוא יפרוס אותו לכונן — המבנה יהיה תקין. היום ה-ZIP מכיל קובץ אחד בשורש.

**מוכן כאשר:** פריסת ה-ZIP שהורד יוצרת את עץ התיקיות המלא עם שני הקבצים במקומם.

## שלב 5 — מיפוי הנתונים

לכל שדה בטבלאות צריך מקור בבסיס הנתונים. שדות שאין להם מקור — או להשלים במודל הנתונים, או להחליט מפורשות שהם ריקים לפי המסמך. **לא להמציא ערכי ברירת מחדל.**

צומת שדורש תשומת לב: שדה מזהה המסמך חייב להיות עקבי בין `C100` (שדה 1204), `D110` (שדות 1257, 1304), `D120` (שדה 1304) ו-`B100` (שדות 1357, 1359). ערך אחד, מקור אחד.

**מוכן כאשר:** יש טבלת מיפוי כתובה — שדה במסמך ← עמודה בבסיס הנתונים ← כלל המרה — שנסקרה לפני היישום.

## שלב 6 — אימות מול הסימולטור

רשות המסים מספקת סימולטור שבודק קבצים. זו בדיקת האמת.

1. להפיק קובץ לתקופת דוגמה עם לפחות מסמך אחד מכל סוג נתמך (305, 320, 400).
2. להריץ בסימולטור עד אפס שגיאות.
3. **ההצלבה של סעיפים 2.6 ו-5.4:** לבנות טבלה שמראה לכל סוג מסמך את מספר המסמכים והסכום, ולוודא שהיא תואמת בדיוק לתדפיסים מהמערכת ולספירת רשומות `C100`.

**מוכן כאשר:** הסימולטור עובר נקי, וטבלת ההצלבה תואמת לאגורה.

## שלב 7 — מה נשלח לרשות המסים

רק אחרי שלב 6: `INI.TXT` + `BKMVDATA.zip` במבנה התיקיות הנכון, פלט הסימולטור הנקי, וטבלת ההצלבה עם התדפיסים.

**אל תשלח קבצים לפני שהסימולטור עובר.** קובץ שנפסל אצלם עולה סבב שלם.
